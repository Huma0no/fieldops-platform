# Corrections

**Version:** 2.0
**Date:** 2026-07-30
**Status:** Closed — confirmed design

## Purpose

How an error on a visit finalized through Generate Report gets flagged, and until when.

## The two moments, and what each one is for

A visit can need a correction at two different times. They are not the same mechanism.

### 1. Before Generate Report — source-data entry
While the technician is still in Workspace, they can enter and correct the Local Visit Draft, including free-text Notes. The draft is durable offline-first working state; Generate Report submits its immutable snapshot, and accepted server source data becomes the shared operational record. This is not a correction-tracking mechanism. See `/docs/OFFLINE-FIRST-CONTRACT.md`.

### 2. After Generate Report, before that visit's Ledger week closes — Request Corrections
Generate Report is the technician's operational finalization boundary: it places the visit in `completed`, `temporarily`, or `cancelled`. After that boundary, the technician does not reopen or directly edit source visit data, nor directly edit generated report text. The technician uses **Request Corrections** (Reports, FieldOps) to flag the error.

**What it is:** one Correction lifecycle, initiated either by the technician or by Dispatch — not a ticket with a formal approve/reject step. A technician Request Correction retains its own request message. Dispatcher-initiated corrections open directly in the editor; an administrative **Note** is optional context, never a gate.

**What happens with it:** Dispatch applies permitted structured source-data changes in Corrections, at its discretion. The canonical Completion Report is regenerated from authoritative visit data; report text is not independently editable. A correction preserves the terminal visit status (`completed`, `temporarily`, or `cancelled`) and never reopens technician Workspace.

**Dispatch boundary:** History opens terminal visits read-only. Corrections is the only administrative editing surface for terminal reports. Every applied correction records its actor, origin, timestamp, affected domains, before state, after state, visit, and correction record in the correction/audit trail. An optional administrative Note is retained when supplied.

**Correction surface:** Corrections edits meaningful structured report source data through domain controls: job context (including scheduled date/time), property context, existing system equipment, service/Finish, catalog-backed thermostat/items (including allowed custom item descriptions/prices), Weigh-In raw measurements, Checklist, and Notes. Total, generated report text, audit metadata, assignment, terminal status, and system topology are not direct correction inputs. Pricing and report output are regenerated by the server; closed/paid Ledger lines remain immutable and use the correction adjustment mechanism.

**Evidence:** photo rows remain historical evidence. The current Corrections contract has no dispatcher photo replacement/removal operation, so evidence metadata is displayed through read-only History rather than treated as a generic correction field.

**Finding a report:** Corrections opens on Find Report. Dispatch may locate a terminal report by exact completion date, inclusive completion-date range, Order #, address, or technician name, then starts the same correction workflow. History details provide **Correct Report**, which transfers that visit into Corrections; History never exposes inline editing.

**Money:** while the applicable Ledger week is open, permitted priced corrections use centrally resolved source pricing and naturally affect the still-open calculation. In a closed or paid week, operational/report source data may be corrected, but closed compensation history is never rewritten. The system records exactly one signed `pay_period_adjustment` for an applied priced correction: corrected compensation minus compensation originally recognized under the source period's historical rate. Positive means additional compensation; negative means deduction. It attaches to the first eligible later open period, or remains pending until that next eligible period exists. The adjustment records its correction, visit, source period, actor, reason, before/after amounts, delta, and timestamps.

**The window:** an open correction expires when its visit's Ledger week auto-closes. An applied correction never reopens that period; a priced closed/paid-period correction uses the immutable adjustment mechanism above.
