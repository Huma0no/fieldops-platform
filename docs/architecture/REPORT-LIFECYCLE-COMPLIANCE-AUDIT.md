# FieldOps Report Lifecycle Compliance Audit

**Audit date:** 2026-11-09

**Scope:** Read-only inspection of current code, schema, migrations, and existing tests against the operational rules supplied with this audit.

## 1. Executive Summary

The clarified model identifies a Visit as one dispatched Service at a Property (physical address). Under that model, Generate Report finalizing a Visit is consistent: the Visit is the Service, and the Property remains available for future Services. The previous audit incorrectly treated one Visit as allowing multiple Reports. The actual cardinality is one Report per Service/Visit, with later Services represented by new Visits at the same address.

The implementation supports multiple Visits at one address and has one `completion_submissions` row per accepted Visit in its normal completion path. Remaining gaps are narrower: the generated report view reads mutable Visit data instead of the retained accepted submission snapshot; a Dispatch reassignment can therefore alter the technician shown for a completed Service; Weigh-In data is keyed to the address and can be replaced by later Services; and the local outbox can overwrite a pending snapshot or mark another submission ID delivered using the wrong ACK. Authentication interruption and photo durability also have independent gaps.

The local draft path preserves `LocalVisitDraft.technicianId` through ordinary local writes, and ambiguous legacy drafts are left unreadable and preserved. The backend records the authenticated technician on each accepted submission and checks the current Service assignment. It does not prove the provenance of an unsubmitted local draft, but the clarified model does not require the backend to register drafts in advance. Pending completion records are not immutable in practice: a repeated Generate Report action while one is pending reuses its ID and overwrites its snapshot. Successful delivery also marks other pending records for that Visit delivered using the first submission's ACK.

`401` handling clears the browser credentials and stops the registered retry trigger, while retaining IndexedDB data. However an already-running retry loop does not re-check authentication between records, and photo uploads bypass the shared `401` expiry event and have no durable blob fallback in the Workspace capture path.

**Overall: PARTIAL against the clarified model.** Do not separate Service completion from Visit finalization based on the earlier audit's incorrect assumption. Prioritize stable per-Service report attribution/content, the outbox identity/immutability defects, and auth/photo recovery. The principal architecture documents' terminal Visit model is consistent with the clarified Service lifecycle. Their “single canonical report derived from Visit data” rule is insufficient for immutable historical Report rendering if the Visit can later be reassigned or its address-level measurements replaced; that specific historical projection boundary needs reconciliation, without implying multiple Reports per Service.

## Operational Model Reconciliation

### Clarified entity relationships

- **Property** is represented by an `addresses` row. It is a durable physical-address anchor, not a work item and has no permanently closed state.
- **Service** is represented by a `visits` row. Dispatch creates each visit/service and may assign it or place it in the Lobby. The schema gives each Visit one required `address_id`, and no uniqueness constraint limits the number of visits at that address (`src/db/schema.sql:170-196`). Manual Dispatch creation resolves/reuses an address and creates a new Visit (`src/routes/dispatch.js:223-287`). Therefore one Property can accumulate many Services/Visits over time.
- **Report** is represented operationally by the accepted completion for one Visit/Service. `completion_submissions` is keyed by `submission_id` and stores `visit_id`, `technician_id`, and a snapshot; its Visit index is non-unique (`src/db/schema.sql:198-208`). The normal completion route inserts one accepted submission then terminalizes that Visit (`src/routes/completion.js:267-304`). Its FK to Visit relates the report submission transitively to the Property through `visits.address_id`.
- Technician attribution is per Service/Report: the Visit has a current technician, and each accepted `completion_submissions` row stores the authenticated technician. The Property itself has no technician owner. Different technicians can perform separate Visits at one address.

### Service completion vs. Report acceptance

FieldOps work on a Service culminates in Generate Report. In the current API, Dispatch acceptance is the successful server-side persistence/ACK of the submission; in the same transaction, the Service/Visit reaches its terminal outcome. That coupling is consistent with the clarified model: it completes one Service, not the Property. The address remains usable for a later Service and Report. No separate Dispatch review/approval state or report-ingestion endpoint was found, so “Dispatch accepts” currently means the server accepts and stores the submission, not a later human approval step.

The previous audit's findings that a Visit must stay In Progress after accepting a Report, and that a second different Report ID must be accepted for that same Visit, came from the incorrect many-reports-per-Service assumption. Those are not requirements under the clarified model. Exactly one Report belongs to each Service; the next issue at the same Property must be a new Service/Visit with its own report.

### Multiple Services and Reports per Property

The database/API can represent separate Services as separate Visits referencing one address. Each completion has its own Visit ID, submission identity, authenticated technician, and stored snapshot. History queries are Visit-based, so separate Services at the address can appear as separate history rows (`src/routes/history.js:46-68, 75-99`). This supports the required cardinality at the entity level; no report-per-property uniqueness restriction exists.

There are two preservation limits. First, report generation uses current Visit rows and current `visits.technician_id`, rather than the accepted completion snapshot (`src/services/report.js:137-185`). Second, Weigh-In data is keyed uniquely by `(address_id, system_number)`, and completion upserts that shared address row (`src/db/schema.sql:245-263`; `src/routes/completion.js:77-100`); a later Service can therefore replace measurements that an earlier Visit's generated report reads (`src/services/report.js:169-175`). The stored completion snapshot retains the earlier payload, but the normal report renderer does not render it. These are historical-report fidelity issues, not a reason to permit multiple Reports for one Service.

### Reassessment of prior findings

- **Generate Report finalizing Visit:** consistent, provided Visit continues to mean one Service. This reverses prior F-02.
- **Multiple Reports for one Visit:** not required; the prior S-03/F-03 concern about a second report ID being rejected after terminalization was based on an incorrect assumption. The local outbox still has an independent immutable-snapshot defect: it overwrites a pending record with the same ID when Generate Report is invoked again, despite the documented immutable pending snapshot contract.
- **Dispatch acceptance vs. Property closure:** previously conflated. Server ACK and terminal Visit status refer to one Service; there is no Property closure operation.
- **Multiple Services/Reports per Property:** supported structurally through multiple Visit rows per `address_id`, with a completion submission tied to each Visit. Historical rendering is not fully preserved because output uses mutable Visit data and address-level Weigh-In state.
- **Historical technician attribution:** a completion row retains its original `technician_id`, but report generation reads the Visit's current technician. The Dispatch reassign endpoint does not reject terminal Visits (`src/routes/visits.js:327-368`), so a completed Visit can be reassigned and its generated report attribution can change. This is a genuine gap; it does not imply that the Property owns a technician.
- **Reassignment from A to B:** if it is the same active Service, A's local pending draft remains tagged A and is not normally deliverable as B; B can work as the current assignee. If B is instead assigned a later, separately created Service at the same Property, that is the expected multiple-Service flow and has a distinct Visit/Report identity.

### Future requirement — Property Service History Context (OUT OF SCOPE)

When Dispatch creates a new Service for an existing Property, FieldOps should eventually give the assigned technician read-only access to that Property's previous Services and Reports. The context must not mutate the current Service or change the historical technician/report ownership. This is a future product requirement only; no design or implementation work is included in this audit.

## 2. Verified Operational Model

The following is directly visible in the current implementation and database:

- `visits` is the mutable operational record. Its schema has one `technician_id`, one `status`, and one set of child work data (`src/db/schema.sql:170-196`).
- `completion_submissions` is a separate table with `submission_id` primary key and `visit_id`, `technician_id`, `terminal_intent`, `snapshot`, and `accepted_at`; `visit_id` has only a non-unique index (`src/db/schema.sql:198-208`, `src/db/migrations/023_completion_submissions.sql:5-15`). The schema can hold multiple rows per Visit, but does not itself provide a report document or versioned source rows.
- The completion endpoint is the sole inspected writer of `completion_submissions`. It writes a row, updates visit child records and `visits.status`, then ACKs in one transaction (`src/routes/completion.js:267-304`).
- The completion report generator reads `visits` and current child tables by Visit ID (`src/services/report.js:137-175`). The completion/download and preview routes call this generator by Visit ID, not submission ID (`src/routes/completion.js:405-441`).
- Dispatch History reads Visits and their current assignee (`src/routes/history.js:46-68`); equipment and refrigerant reports aggregate current Visit/work rows (`src/routes/reports.js:16-34`, `75-94`). No inspected dispatch endpoint ingests or lists independent completion submission records. This is code-path inspection, not a claim about external systems.

The core lifecycle in the current architecture matches the clarified model: `docs/ARCHITECTURE-MAP.md:13-25, 48-55`, `docs/OFFLINE-FIRST-CONTRACT.md:44-69`, `docs/shared/API_CONTRACT.md:447-481`, and `docs/shared/DATA_MODEL.md:284-312` all define one terminal completion per Visit and a derived Completion Report. Here Visit is interpreted as Service. The limitation is that a derived report over mutable Service/Visit and Property-level Weigh-In data may not retain historical report content or author attribution after later changes; the docs' “no report snapshot or versioned editable copy” language in `docs/ARCHITECTURE-MAP.md:55-57` conflicts with the requirement that historical Reports retain their own Service/technician identity and unchanged accepted content. The prior audit's claim that a Visit must remain In Progress and accept further Reports is withdrawn.

## 3. Visit vs. Report Lifecycle

The current API couples the two lifecycles. It accepts submissions only while a Visit is `assigned` or `in_progress`, then sets it to `completed`, `temporarily`, or `cancelled` (`src/routes/completion.js:223-235, 258-304`). A new submission ID against a terminal Visit receives `409`, even when the request is from the current assignee (`src/routes/completion.js:223-230`). Only a retry whose ID already exists can receive the normal idempotent ACK.

The report returned for initial acceptance and retries is generated from the Visit's live rows. A stored `snapshot` is not used to render that response (`src/routes/completion.js:217-219, 303-304, 378-386`; `src/services/report.js:137-185`). Therefore the table preserves some accepted payload and author metadata, but downstream report/history behavior does not use it as an independently addressable historical report.

Generate Report finalizing one Visit/Service is consistent with the clarified model; no separate Service completion transition is required by this audit. The genuine gap is report-history fidelity: report rendering by Visit currently reads mutable Visit state and does not select the accepted submission snapshot. The minimum correction is to make an accepted Service Report render with that Service's accepted technician/content despite subsequent reassignment or changes to shared address data. That correction need not permit multiple Reports for one Service.

## 4. Draft vs. Submitted Report Lifecycle

### LocalVisitDraft.technicianId

`createLocalVisitDraft` initializes `technicianId` from the visit detail (`frontend/pwa/src/lib/workspace-visit.mjs:183-196`). Workspace first reads the local draft using the active technician; only if none exists does it GET current Visit detail, verify the current assignee, and create/save a draft (`frontend/pwa/src/screens/workspace.js:103-129`). `saveLocalVisitDraft` rejects a mismatch between the draft's technician and the explicit/current technician, and stores the value with the record (`frontend/pwa/src/lib/db.js:179-202`). A dirty draft is retained by `seedLocalVisitDraft` (`frontend/pwa/src/lib/workspace-visit.mjs:217-219`). Thus the field functions as the draft's original local owner after creation, not a value refreshed from reassignment during normal save. It is initially equal to the current assignee because initial creation follows an ownership-checked Visit fetch.

These are client-side safeguards. A local draft and its `technicianId` are not registered with the backend before submission. Completion validates that a declared snapshot technician equals both the authenticated identity and current Visit assignee (`src/routes/completion.js:156-174, 197-200`), but cannot independently prove who originally authored the draft. The snapshot field is a client assertion.

### Submission snapshot and outbox

`createCompletionSnapshot` embeds a stable ID, Visit ID, and technician ID (`frontend/pwa/src/lib/completion-submission.mjs:66-90`). But when called without an explicit ID, `createPendingCompletionSubmission` finds any pending record for that Visit, reuses its ID, rebuilds the snapshot from current draft content, and saves over it (`:93-116`). Multiple reports for one Service are not required, but this still violates the documented rule that once a pending submission snapshot is created it remains immutable across retries. The UI should not turn a second Generate Report attempt into a different payload under the already-created stable identity.

On successful delivery, the code marks the matching record delivered, then marks every other pending record for the same Visit delivered with the same ACK, without verifying each `submissionId` against that ACK (`frontend/pwa/src/lib/completion-submission.mjs:139-165`). The retry loop intentionally tries at most one record per Visit per pass (`:181-203`), which is compatible with one Report per Service but can strand a conflicting legacy/duplicate record. Existing tests codify reuse-and-overwrite (`tests/completion-submission.test.js:213-224`) and delivery/reconciliation of a second ID using the first ACK (`:226-258`). The latter is an outbox identity bug; it is not evidence that two reports per Service should be accepted.

The minimum correction is to preserve the first pending snapshot under its stable ID and mark delivered only the record whose exact submission ID the backend ACKs. A second Generate Report attempt for the same Service should follow the one-Report-per-Service lifecycle rather than mutating the already-pending accepted payload or creating a second accepted Report.

## 5. Reassignment and Historical Ownership

Dispatch reassignment updates `visits.technician_id` and retains the current status except for lobby/review states (`src/routes/visits.js:327-368`). Transfer acceptance similarly changes the Visit assignee in a transaction (`src/routes/transfers.js:133-150`). Neither path changes `completion_submissions` rows, which retain their own `technician_id` and `snapshot`.

That retained row is not the source for report output. `generateReportJSON` selects `v.technician_id` and current Visit children (`src/services/report.js:137-185`); report/history views use the same mutable Visit model. Dispatch's reassign endpoint accepts terminal Visits and changes the assignee without updating the completion row (`src/routes/visits.js:327-368`). If a completed Visit is reassigned, generated output can show B as technician even though the accepted completion row and snapshot still say A. This is a real risk to historical Report attribution. It is separate from B performing a new Service at the same Property: Dispatch can create another Visit for the existing address, and that new Visit can be assigned to B.

For an unsubmitted A draft, local ownership checks keep the draft tagged to A and reject normal delivery under B's active identity (`frontend/pwa/src/lib/db.js:179-202`; `frontend/pwa/src/lib/completion-submission.mjs:119-138`). Backend current-assignment validation rejects A after reassignment and requires the request's declared technician to match B. It cannot independently prove whether B's newly submitted content was authored from a new local draft or copied from earlier work; there is no server-side draft-origin record. The established model requires report attribution to come from the authenticated technician on the Service, which the accepted row does. Any stronger provenance rule for an unsubmitted local draft would need a specific product requirement; it should not be inferred as a new ownership infrastructure requirement.

Existing reassignment tests cover assignment/status/notification behavior, not completed-Service report attribution after reassignment (`tests/visits.test.js:450-579`). Existing completion tests verify F-02 reassignment ownership checks under a Visit row lock (`tests/completion.test.js:447-525, 574-707`), not historical report rendering.

## 6. Device Ownership Assumption

This audit assumes one technician per FieldOps installation, as explicitly required. It does not assess same-device technician switching or require cross-user IndexedDB isolation architecture. The current database helper has technician-scoped keys/read checks (`frontend/pwa/src/lib/db.js:37-70, 179-259`), but that broader behavior is outside this audit's operating model. The relevant property here is only that reassignment must not change the original technician tag of a local draft or accepted submission.

## 7. Authentication and Offline Recovery

### Pending completion submissions

The ordinary authenticated `request()` helper clears localStorage credentials and emits `auth:expired` on HTTP 401 (`frontend/shared/api.js:25-45`). App handling calls `clearSession()` and shows authentication (`frontend/pwa/app.js:110-114`); a successful same-technician invite redemption triggers the queue retry startup again (`frontend/pwa/app.js:153-161`). IndexedDB readers return no owned data while unauthenticated, but do not delete it (`frontend/pwa/src/lib/db.js:385-416`; preservation test `tests/local-visit-draft.test.js:272-277`). Same-technician recovery can read and retry its pending snapshot after restoring a session (`tests/completion-submission.test.js:350-392`).

There is a concurrency gap in the 401 stop guarantee. `stopCompletionSubmissionRetry` removes the online listener and resets the startup flag (`frontend/pwa/src/lib/completion-submission.mjs:221-228`), but an already-running `retryPendingCompletionSubmissions` loop continues over its previously read list and never re-checks active authentication after an awaited delivery (`:181-203`). The test named “halts retries during authentication expiration” clears credentials before starting retry, so it verifies no-auth guard and data recovery, not a 401 occurring during a multi-record retry batch (`tests/completion-submission.test.js:350-392`). A minimal correction is to stop the current batch immediately after a 401/auth-expired signal and before starting another request; keep all pending records unchanged.

### Photos

The IndexedDB layer exposes local photo blob storage (`frontend/pwa/src/lib/db.js:438-460`), but the two Workspace capture handlers send the compressed image directly to `/visits/:id/photos` and only update local UI state after upload (`frontend/pwa/src/screens/workspace.js:958-979, 1100-1114`). On failure they log and return; they do not call `addPhoto` or preserve the Blob. The server route inserts photo metadata with `stored_at = null` and does not persist the multipart bytes (`src/routes/workspace.js:543-589`; schema `src/db/schema.sql:265-274`). Moreover, `api.upload` throws for 401 without clearing auth or dispatching `auth:expired` (`frontend/shared/api.js:64-87`). A failed/offline capture can therefore be lost, and a revoked token on upload does not trigger the global session-stop path. The smallest correction is durable blob persistence before upload, retry/cleanup tied to upload success, and shared 401 expiry handling for uploads. Contract § photos explicitly requires durable local blobs before successful upload.

## 10. Unresolved Questions and Decisions

1. **Dispatch acceptance meaning:** The inspected API has server persistence/ACK but no separate human Dispatch review/approval state for a completion Report. Confirm whether server ACK is the full intended meaning of Dispatch storing the Report.
2. **Historical report after correction:** The canonical architecture says corrections update Visit source and derived artifacts regenerate (`docs/ARCHITECTURE-MAP.md:9-13, 55-57`). The earlier operational rules require accepted report content/author to remain historical. Decide whether a correction creates a revised Service report view or changes only current Service data; this audit does not design that workflow.
3. **Photo evidence requirement:** The offline contract requires local Blob durability before upload; it leaves open whether all required evidence must upload before a completion Report ACK. Preserve that open decision rather than silently gating acceptance.
4. **Property Service History Context:** The read-only prior-Service/Report context is recorded as future and out of scope above; access policy and presentation can be specified when that feature is authorized.
